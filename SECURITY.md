# Security

How this app keeps keys and data safe, and what you need to do when you host it yourself.

## Where secrets live

| Secret | Where it goes | Never put it in |
| --- | --- | --- |
| Supabase URL and publishable key | `apps/app/.env` (shipped in the app; safe because of row-level security) | — |
| `PLAID_CLIENT_ID`, `PLAID_SECRET`, `CRON_SECRET` | `supabase/.env`, uploaded with `npx supabase secrets set --env-file supabase/.env` | `apps/app/.env`, the repo |
| Supabase secret (service-role) key | Provided to Edge Functions by Supabase; you never copy it | Anywhere in the app or repo |
| Bank access tokens | Supabase Vault (encrypted), written and read only by Edge Functions | The browser never receives them |

`.env` files are git-ignored. `supabase/setup/cron.sql` is committed with placeholders only: paste it into
the SQL Editor and fill it in there. Do not save the filled-in copy back to the repo.

## How data is protected

- Every table has row-level security: a signed-in user can only read and write their own rows.
- Bank connections (`plaid_items`) and sync history are read-only for users; only Edge Functions change them.
- Signed-out visitors have no access to any table.
- The functions that store, read and delete bank tokens can only be called with the secret key.
- Edge Functions check the caller's sign-in token themselves; the daily sync also accepts the cron secret.
- Demo accounts (`app_metadata.demo = true`) cannot link banks, in the app or by calling the functions directly. To make one: `update auth.users set raw_app_meta_data = raw_app_meta_data || '{"demo": true}' where email = '…';`
- Receipt photos and nightly backups are kept in private storage buckets (`receipts`, `backups`), in a folder per
  user; the bucket rules only let a signed-in user reach their own folder, and backups can only be written by the
  Edge Function. Backups hold the same tables as Settings → Download everything, never bank tokens.
- Sample data is created by a database function that runs as the signed-in user, so it can only touch that user's rows.

## Offline copy on the device

So the app can be read without a connection, the answers to what you've looked at are saved in the
browser's storage on that device (`apps/app/src/lib/offline.ts`).

- They are encrypted with AES-GCM. The key is generated by the browser and stored as
  non-extractable: the app can use it, but it can't be read out or copied.
- This protects against someone reading the device's storage. On its own it does not lock the app: anyone
  who can open the app on an unlocked device sees what you would, and the sign-in itself is kept
  in the same storage. Turn on the app lock (below) to close that.
- Everything saved, and the key, is deleted on sign-out. Saved answers older than 30 days are dropped.
- Nothing is queued offline; changes are refused until the connection is back.

## App lock (optional, per device)

Settings → App lock asks for a fingerprint (or face) or a PIN before the app opens
(`apps/app/src/lib/lock.ts`). It asks on every fresh start and after 5 minutes in the background.

- Turning it on creates a random key that encrypts the saved sign-in and the offline copy. The
  key is stored only in wrapped form: once under a key derived from the PIN (PBKDF2-SHA256,
  600,000 rounds) and once under a secret the device's passkey returns after checking the
  fingerprint (the WebAuthn PRF extension). It is in memory only while the app is unlocked.
- Where the device or browser doesn't support that passkey secret, the fingerprint is a check in
  front of the app and the key is held by the browser as non-extractable instead; the PIN still
  wraps it. Settings shows which of the two applies on the device.
- A 6-digit PIN can be guessed by someone who copies the device's storage and tries every PIN
  offline (the 600,000 rounds slow that down, they don't prevent it). A longer PIN (up to 12
  digits) is stronger. On the lock screen itself, wrong tries are slowed after five.
- A forgotten PIN can't be recovered. "Sign out and clear this device" erases the saved sign-in,
  the offline copy and the lock; the account itself is untouched. Signing out also turns the lock off.
- The fingerprint check is local to the device. Nothing about it is sent to or checked by the server.

## Settings to check in the Supabase dashboard

- Authentication > Sign In / Providers: turn off "Allow new users to sign up" and add users yourself.
- Authentication > Attack Protection: turn on leaked-password protection if your plan has it (not on the free tier).
- Use a long unique password. Anyone with it can read your finances.

## Known limits

- Edge Functions answer any website (`Access-Control-Allow-Origin: *`). They still require a valid sign-in token.
- Error messages from Plaid and the database are passed to the signed-in user as-is.
- Merchant and bank logos are fetched from DuckDuckGo's icon service by site name. Turn this off in Settings.
- `npm audit` reports issues in Expo's build tools (node-forge, uuid). They run at build time and are not shipped in the app.
